# Communication Center parity checklist

The existing desktop Documents & Communication form links to the web Communication Hub and CRM Files. The web center groups Overview, Inbox, Compose, Campaigns, Templates, Automations, Analytics and Settings in `frontend/src/apps/communication/CommunicationHubPage.tsx`. No web development server was listening on ports 3000, 4173, 5173 or 8000 during this audit. Live comparison is outstanding.

## Local records and workflow

- [x] Native email template browsing, literal name/subject search, optional disabled rows, view, create, edit, soft disable and enable on save. The designer-defined grid and editor use the existing templates and branch-stamped timeline. The plain text body supports merge-field text and safely encodes edits in the web rich-text storage format. Metadata-only edits preserve existing rich layouts.
- [x] Template CSV export is available from the designer-defined Communication Center list. It exports only the currently loaded, permission-scoped rows, uses RFC-compatible quoted fields, UTF-8 encoding, and an overwrite-safe Windows save dialog; it remains available offline without provider delivery.
- [x] Delivery history and customer-reminder lists expose the same designer-defined CSV export action. Export is limited to the filtered rows already loaded under the current branch scope; provider status is preserved as recorded and no delivery is attempted.
- [x] Template history modal with time, event, subject and summary. Uses the template and timeline view permissions and selected company/branch.
- [x] Offline email drafts. Pick a branch-visible lead, contact or company, preload an active template if selected, edit recipient/subject/message, resolve `{{name}}` and `{{email}}`, and save the draft and related timeline event atomically. Search saved drafts by recipient, CRM record or subject and reopen the message body. Desktop requires CRM company administration plus applicable module grants for these CRM picker workflows.
- [x] Local working draft autosave and clear follow `center/EmailComposer.tsx`. The desktop protects the recipient reference, address, subject, unrendered body and merge values using the Windows account and scopes the file to the database configuration, login, company and branch. Reopening checks the record through the same scoped picker permission before enabling PostgreSQL save. Clear removes the working copy without changing saved PostgreSQL drafts. The working copy stays on the workstation.
- [x] The composer can check recorded email opt-out using `engagement_api.py` and `services/delivery.py`. A hard opt-out takes precedence over later consent. Without a hard opt-out, the most recent Email consent determines the result. Desktop reads only suppression and consent rows owned by the selected company through the `tenant_boundary.py` legacy ownership convention. The check also requires a visible selected record and a visible CRM address. Saving the draft is still available.
- [x] Native linked Email consent history and Record customer choice follow `center/GuidedTools.tsx` and the consent handlers in `api/router.py`. The dialog displays company-owned evidence for the selected record and current address. A consent manager in the record’s owning branch can review and record opt-in, opt-out or unsubscribe with evidence. Saves append the consent, company ownership and authenticated branch audit and reject stale revisions. Unlinked choice entry and WhatsApp consent remain open.
- [x] The consent dialog supports the address-wide suppression action from `POST /communication/opt-out`. It previews the company-wide effect, records the suppression and linked consent with their verified company ownership, and audits the original evidence-bearing record. Repeating the same action preserves the original row. A later opt-in leaves the address-wide block in force. If the legacy database-wide email/channel uniqueness constraint is already occupied by an inaccessible suppression, the desktop reports that the action could not be saved and leaves both companies’ records intact.
- [x] Template favorites follow `CommunicationHubPage.tsx`. Users can favorite or unfavorite a template and combine Favorites only with search and the disabled filter. Favorites persist per Windows profile, database configuration, signed-in user, company and branch. The template query still applies all record permissions and branch scope before displaying a favorite.
- [ ] Rich-content editing at `/crm/email-templates` remains open. The designer-defined native editor now supports reusable `{{name}}`, `{{email}}`, `{{phone}}`, and `{{company}}` merge-field insertion into either subject or body, matching the draft composer placeholders; PostgreSQL storage and branch/audit rules remain unchanged. Rich layout authoring still requires the provider-compatible rich-text editor contract. See `schemas.py`, `models.py`, `backend/app/access/scope.py`, and `backend/tests/test_communication_email_templates.py` and `test_communication_rbac.py`.
- [x] Offline email draft merge fields and plain-text preview follow `center/EmailComposer.tsx`. The native dialog lists custom placeholders from both subject and body in a fixed two-column grid, resolves name and email from the current draft, and previews the resolved recipient and message. The repository uses the same rendering and rejects unresolved or invalid drafts before saving.
- [x] Native Quick replies follow `center/shared.tsx` and `center/EmailComposer.tsx`. The composer button or slash on an empty body opens the three built-in replies, literal name/body search, favorites, and custom replies. Using a reply appends it to the message and preserves merge placeholders. Replies and favorites persist offline in the Windows user profile, scoped to the verified database configuration, signed-in user, company and branch.
- [ ] Richer template layout previews, dispatch recipient eligibility and consent checks, and separate confirmation before dispatch. See `center/EmailComposer.tsx`, `EmailDraftPayload`, `_create_email_message` and `services/delivery.py`.
- [x] Customer Notes workspace searches existing recipients by name, email, and telephone in the selected company and branch. It reads persisted internal history and adds attributed internal notes with the web note permission and writable branch check. Posting an internal note performs no provider operation.
- [x] Customer email history shows stored inbound replies and outbound delivery records with message text, direction, date and status. Each reply must match its parent email delivery, recipient, company and branch. Root QA verified both directions and cross-branch rejection through the native repository. Provider ingestion and dispatch remain separate.
- [x] New customer notes can record an assignee and optional follow-up time. Assignees must be active and eligible for the selected company and branch at save time. The desktop stores an absolute timestamp, displays it in workstation local time, and shows whether the reminder was processed. Isolated QA verified the assignee, timestamp, unset reminder state, and rejection of an unavailable assignee.
- [x] Process my reminders claims due, eligible notes created by the signed-in user in the selected branch. It saves the existing in-app notification, branch ownership and processed timestamp atomically. Isolated QA verified one notification across concurrent processing and retry, and exclusion of future notes.
- [x] My reminders opens searchable in-app customer follow-up notices for the current user and branch. It displays the persisted notice and read state. Unread only, Mark as read and Mark all read follow the personal notification handlers in `api/v1/notifications.py` and the notification model. The desktop retains reminder, actor and branch scope for every update.
- [ ] Inbox across channels, matching and customer workspace. Inbox filters include channel, queue, contact type, owner/team, status, date, priority and tags. Thread detail supports per-user read/snooze, assignment, workflow updates and record links. Recipient CRUD, CRM bindings, automatic processing when the creator is away, and the general notification inbox remain open. See `center/EngagementInbox.tsx`, `CustomerCommunications.tsx`, `engagement_api.py`, `engagement_models.py`, `customer_api.py` and `customer_models.py`.
- [x] Local Delivery history view for branch-owned provider logs and customer delivery records. Search, channel and status columns, and the Needs attention filter surface failed, blocked and uncertain records without triggering provider activity. Provider request and response payloads stay out of the view. Invoice-linked delivery evidence is withheld pending SRM invoice authority and seller-context checks.
- [x] Delivery history filters by Email or WhatsApp before the record limit. This follows the channel filter in DeliveryWorkspace.tsx and combines with the native text and Needs attention filters. Customer email history and My customer reminders retain their own filters.
- [x] Filter Delivery history by exact standard status before the result limit. Status combines with channel, text search and Needs attention. Unlisted provider statuses remain visible through All statuses and the grid filter.
- [ ] Full Delivery workspace, timeline and overview. Add authorized invoice evidence, WhatsApp message and receipt evidence, links to inbox conversations, and broader reporting. Preserve history independently of current provider connectivity. See `center/DeliveryWorkspace.tsx`, `TimelineExplorer.tsx`, `CommunicationHome.tsx`, the `/delivery-logs` and `/timeline` handlers, and `test_communication_timeline.py` and `test_communication_center_summary.py`.
- [x] Edit existing customers' transactional, marketing, and greeting email preferences. The native editor follows the consent fields and evidence in `CustomerCommunications.tsx`, the recipient PUT handler in `customer_api.py`, and `CustomerRecipient`. It checks current company and branch, uses a revision, and requires consent-management permission for a new opt-in. Saved changes append consent history and the existing recipient-preferences audit. Other channel preferences are preserved.
- [ ] WhatsApp consent and contact identity synchronization, customer preference links, reminders and contact birthdays. Keep consent and manual preparation available offline where supported, and enforce consent before dispatch. Trace `center/SendReminders.tsx`, `GuidedTools.tsx`, shared follow-ups and `test_communication_opt_out.py`.
- [x] Native Email campaigns follows `center/CampaignWorkspace.tsx`, the campaign handlers in `api/router.py`, and `test_communication_campaigns.py` and `test_communication_campaign_consent.py`. List and search branch-owned campaigns. Review and save a named draft using an authorized active template, a Lead or Contact audience, an optional CRM status and a limit of 1–50. Preview displays company-scoped suppression, invalid email, and a personalized sample. Draft and cancelled records can be edited with a revision check. Draft and scheduled records can be cancelled and retained. Creation, editing and cancellation record an authenticated branch audit.
- [x] Campaign history opens the persisted creation, edit and cancellation audits and currently visible delivery records for the selected branch. The web campaign detail and send handlers store members and direct attempts. The scheduled worker in `services/email_schedules.py` stores an outbox record with a campaign and address-derived event key. Native history checks the campaign, company, current CRM recipient and any recorded branch ownership. It distinguishes members, direct sends and scheduled-worker events. Recipient delivery remains unconfirmed for sent and accepted states. Provider request, response and error text stay out of the display.
- [x] Local webform acknowledgement rules follow center/GuidedTools.tsx, the auto-response rule handlers, and test_communication_auto_response.py. Search and list existing branch-owned rules. Review and save a named webform_submission rule with an authorized active email template and optional active status. The rule, branch ownership and actor audit are written atomically. The native webform draft can attach a rule.
- [x] Customer webform list, search and draft creation follow the Guided Tools screen, the form schema and create handler, and test_communication_company_forms.py, test_communication_webforms.py and test_communication_engagement.py. Review a Lead or Contact target, public slug, required flags, field input types and unique CRM mappings. Optionally attach a branch-owned active acknowledgement rule. PostgreSQL stores the canonical field and mapping JSON, branch ownership, creation timeline and audit in one transaction. New forms are inactive to avoid exposing a form through a connected web server by saving an offline draft.
- [x] Deactivate an active branch-owned webform after review. The web DELETE handler sets the active flag to false and keeps the definition and submissions. The desktop requires webform management and the delete action, checks the selected row revision and creator scope, and adds a timeline event and branch audit in the same transaction.
- [x] View saved webform configuration using the web detail handler and the public form's field/mapping shape. The native dialog lists the stored status, CRM target, slug, acknowledgement rule reference, fields in saved order, and any mapping whose source key lacks a field definition. Company, branch, view permission and creator scope are enforced when opening the record.
- [x] Edit an inactive Lead or Contact webform with the supported field and mapping structure. Review changes to the name, slug, target, field definitions and rule. The write follows PUT /webforms/{id}, verifies branch and creator scope and edit permission, checks the loaded revision, and writes a timeline event and audit. Configurations with extra field metadata or unsupported mappings remain readable and are protected against destructive rewrites.
- [x] Activate an inactive Lead or Contact form after explicit review. The action validates the saved configuration and an attached acknowledgement rule, checks write permission, branch ownership and revision, and updates the same active flag used by the web public GET and POST handlers. The review explains that a connected public server can immediately accept submissions. An activation writes a timeline event and branch audit without submitting the form.
- [x] Edit an active form in place using the same supported field and mapping rules. Review explains that a connected public endpoint reads the saved definition immediately and that changing the slug retires the previous URL. The update preserves active status and existing submissions. Public form display, submissions, duplicate handling, and acknowledgement delivery require a connected public endpoint and provider where applicable.
- [ ] Campaign dispatch, scheduling, retries, and automations. Dispatch and schedules require the corresponding provider and worker. The offline desktop creates no scheduled sends. Remaining local automation setup and reporting follow `AutomationWorkspace.tsx`, the automation handlers and `test_communication_auto_response.py`.
- [ ] CRM Files. The existing desktop shortcut has no native file workflow. Audit separately for local file retention, storage connections, record permissions, and provider-only sharing.

## External prerequisites

- [ ] WhatsApp inbox ingestion, send, templates sync, business profile, analytics and setup require Meta WhatsApp connectivity. The web onboarding, webhook and media paths are in `frontend/src/apps/communication/whatsapp`, `backend/app/api/v1/whatsapp_cloud.py`, and `backend/app/services/whatsapp_*.py`. Persisted history remains a separate local workflow.
- [ ] Email delivery needs a configured and reachable provider and delivery worker; public form submissions, consent/preference links and email/WhatsApp webhooks need a reachable web endpoint. Desktop must not claim delivery or enqueue unsendable work. Local draft and setup data can still be retained as their workflows are ported.
