# Appointments desktop parity checklist

## Reference paths and behavior

- Entry routes `/srm/appointments` and `/crm/appointments` both select appointment mode in `frontend/src/apps/srm/industry/IndustryOperationsPage.tsx`. This displays day/week timeline, date and resource context, loading/empty states, and an agenda with details and permitted actions. `ServiceSchedulingWorkspace.tsx` opens the same booking flow from a calendar slot or a prebooking panel. Existing desktop form links to a placeholder.
- New appointment selects a shared customer account, active Sales catalog service, eligible employee/provider, optional room/chair/equipment/location resources, booking date/time and duration, internal/customer notes, walk-in and optional confirmation channels, PMS project/task and CRM opportunity. The confirmation reviews current availability and pricing, does not collect payment and maintains an idempotency request identity if the response is uncertain. Service schedule settings and staffing determine availability.
- `backend/app/apps/srm/industry_api.py` implements scoped appointment/resource list and detail, request status, create, reschedule and state transitions. `industry_models.py` stores the canonical appointment and resource in `srm_industry_records`, keyed by company, branch and request identity. Create snapshots customer, service price/tax/currency, timestamps and resource IDs. Row revision prevents stale reschedule/transition. No-show requires past start and reason. Cancellation requires a reason and releases capacity. Check-in, in-service and completed state transitions must follow the allowed sequence.
- Native access checks in `industry_api.py` and `business_packs/operations.py` layer Sales permissions, enabled modules, current branch, operational-pack capability and provider/data visibility. Grouped POS service appointments reschedule through their own checkout occurrence link. A reschedule of a project-linked appointment also updates its PMS task in the same transaction.
- `service_checkout_options.py` checks active policy and active/effective specialist eligibility, versions, provider/employee identity, allowed duration, matching resource selection and appointment availability. `service_resource_requirements.py` derives required room/chair/equipment/location types from catalog metadata. `business_packs/availability.py` checks resource hours and overlap, employee leave, same employee/user across branch resources, capacity with half-open intervals and malformed existing data. Writers hold the same company advisory and row locks.
- Relevant regression tests include `test_prebooking_experience.py`, `test_prebooking_shared_selection.py`, `test_prebooking_resource_requirements.py`, `test_prebooking_concurrency.py`, `test_booking_resource_capacity.py`, `test_service_scheduling_concurrency.py`, `test_appointment_booking.py`, `test_appointment_checkout.py`, and `test_appointment_billing.py`.
- Web frontend listeners were not running on the local development ports at audit start. Desktop installation contains the existing WinForms form shell and Telerik grid assemblies.
