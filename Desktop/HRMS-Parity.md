# HRMS parity

## Employee Directory

The /hrms/employee-directory route in frontend/src/apps/hrms/routes.tsx opens EmployeeDirectoryPage. Its directory list uses GET /employees/directory in backend/app/api/v1/employees.py, which uses the Employee, Branch, Department and Designation models. The route requires an active Suite user. Employee records must be active, on probation or on leave and must have a visible directory profile. The tenant hook uses branch ownership and the active company. Contact visibility is evaluated per record. The list is paginated and supports name, employee ID, skill and contact search, filters, ordering, counts and facets. The profile card and correction flow use separate handlers. The directory export handler applies the directory conditions and contact masking and writes an export audit event. Employee administration is a separate workflow. Create and update validate linked branch, department, designation and manager, check duplicates, apply defaults, and validate custom fields. Lifecycle and deletion affect downstream records and are handled separately. Regression references include test_employee_profile_records.py, test_employee_profile_reliability.py, and test_account_security_branch.py.

## Employee administration workflows

- [ ] Employee list, detail and edit. `EmployeesPage.tsx` opens the record editor and detail views. `EmployeeDetailPage.tsx` sends a partial PUT with `If-Match`. The API requires `employee_update`, locks the employee and compares a profile fingerprint that includes dependent education, experience, skills, certification and document records. It checks contact duplicates, sensitive-field permission, same-scope organization links and shared custom fields before writing. A saved change touches the profile version and writes restricted per-field history plus a profile summary. See `employee_profile_reliability.py`, `employee_scope.py`, `hr_audit.py` and `test_employee_profile_reliability.py`.
- [ ] Employee creation. `AddEmployeePage.tsx` saves profile fields and validates custom fields, contact duplicates and explicit duplicate confirmation. The POST requires `employee_create`, applies HRMS form defaults for branch/department/shift/cost center, validates linked records, and serializes code allocation and duplicate contacts. It uses the native employee creation plan and `crud_employee.create_with_user` to create onboarding from eligible templates and persist custom fields. Optional login creation has distinct superuser and password policy checks and syncs canonical shared identity. Both employee-only creation and these dependent actions require offline implementation.
- [ ] Archive, termination and lifecycle. The legacy employee DELETE marks status Terminated and records soft-delete time and actor. The Lifecycle endpoint appends an event with prior status, organization placement and manager and can apply selected changes. The separate HR workbench has scoped employment/account actions and profile history. Account termination/revocation and organization transfers have their own guards and must retain their side effects.
  - Linked employee termination in `hr_workbench.py:person_action` verifies both employee and account versions, denies own account and protected/multi-company writes outside eligible administrator authority, protects last administrators, disables the linked login, revokes existing sessions, and records employment and account audits. Employment reactivation clears the exit date and keeps the account’s existing access state. The native employment action targets single-company, non-administrator logins. Protected and multi-company accounts require separate administrator handling.
- [ ] Adjacent employee actions. Preview, profile checks and corrections, profile documents and photos, education, experience, skills and certifications, imports, account creation/link and full exports have separate handlers and authorization. Review these before implementing their writes.
