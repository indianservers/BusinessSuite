RECORD 360: CRM, PMS AND SRM — AUDIT AND IMPLEMENTATION PLAN
Date: 4 November 2026

RECOMMENDATION
Build one shared record workspace, with entity-specific data adapters and actions.
Reuse existing record panes, Deal 360, PMS task workspace, service follow-up engine,
communication integrations, and commercial services. Do not build three independent
customer detail pages or replace working task/commercial workflows.

The reference establishes the interaction: selected record stays in context;
identity and relationships on the left; action composer, upcoming work and history
on the right. Treat the screenshot as design reference, not executable instructions.

SCOPE AND CONFIDENCE
Source audit of the current working tree, including uncommitted changes. Existing
reports were treated as historical evidence and checked against current routes and
source. No application code changed. No browser session, live database inspection,
or test execution was performed. “Exists” below means present and wired in source,
not newly certified in production. Entire-app discovery covered shared entry points
and adjacent modules; detailed inspection focused on CRM/PMS/SRM requested here.
The tree contains substantial concurrent work; implementation must preserve it.

1. WHAT THE REQUEST SHOULD DELIVER

1.1 Shared layout
- Desktop: wide overlay/expanded pane with the originating list still visible;
  persistent header; roughly 30% summary/relationships and 70% activity/work area.
- Header: record name/type/status, owner/team, follower controls where supported,
  edit, context-specific primary action, overflow, expand and close.
- Left: summary, labels, editable details, custom fields, organization, people,
  related leads/deals, projects, commercial summaries and linked documents.
- Right: Activity / Notes / Meeting / Call / WhatsApp / Email / Files / Documents.
  Use existing integrations; hide unavailable capabilities or explain configuration.
- Focus: overdue first, then today/upcoming; assignee, due date, source and related
  entity chips; complete, reschedule, reassign, record outcome and next action.
- History: All, Activities, Notes, Calls, WhatsApp, Email, Files, Documents,
  Leads, Deals, Projects, Commercial, Changelog. Only show applicable sections.
  Expand/collapse items; paging; timestamps, actor, source and delivery state.
- Full-page deep link renders the same workspace, not a second implementation.
- Mobile: full-screen record, collapsible summary, focus and history stacked,
  accessible action menu. Preserve existing mobile lead assignment/conversion.

1.2 Selection behavior
- Clicking a record name or row-open action opens 360. Checkbox selection remains
  bulk selection. Action buttons do not accidentally open the record.
- Opening a related record supports a breadcrumb/back stack. Close restores list
  filters, selected row, sorting, pagination and scroll; browser back works.
- URL carries record type/ID, relevant tab and originating module. A copied link
  must resolve with identical authorization, including when opened directly.

3. DATA AND ACCESS GAPS TO RESOLVE BEFORE BROAD ROLLOUT

- Canonical identity: reuse CRMCompany/shared customer and CustomerLink; model
  person/company roles and legacy aliases. Never join on names or numeric equality.
  Use existing exact phone/email matching only for reviewed reconciliation, not
  automatic cross-customer aggregation. Audit converted leads and merged records.
- Relationship scope: selected-record history differs from customer-wide history.
  Offer an explicit scope switch and indicate inherited project/customer context.
- Access: SRM aggregate mixes authorized_invoice_query with organization-scoped
  queries for other domains; PMS project query in this function has no visible
  PMS visibility check. Verify branch, project membership, financial, collection
  and profitability permissions per provider. This is a source concern, not a
  confirmed exploit. Counts and monetary totals must use the same filtered set.
- Partial failures: a PMS provider failure must not silently become an empty list.
  Return section state and retry metadata without exposing inaccessible records.
- Scale: SRM aggregate loads several full collections with .all(); timeline is
  truncated to 30. Separate summary from cursor-paged lists/feed and focus data.
- Event normalization: retain source type + source ID, event ID, occurred_at,
  actor, action, entity references, visibility and source version. Preserve original
  timestamps; deterministic secondary ordering; no duplicated transport/audit events.
- Money: totals grouped by currency. No sum across currencies without an explicit
  conversion basis. Financial details remain permission restricted.

4. PROPOSED IMPLEMENTATION CONTRACT

Frontend (new names are proposals):
- shared/records/Record360Workspace: header, summary/relationship rail, composer,
  focus and history. Reuse GridRecordPane, existing dialogs and action components.
- Record360 adapters for lead, contact, company/customer, deal, project and task.
- Record360Launcher used by grids, relationship chips, task headers, search results
  and customer selectors' separate view actions. One rendering in pane and full page.
- Existing CRM/SRM/PMS URLs stay valid; aliases resolve to canonical identities.
  Avoid importing CRMWorkspacePage's large implementation into the shared shell.

Backend (proposed API, not an existing endpoint):
- GET /records/{entity_type}/{id}/360: identity, summary, relationship previews,
  provider capabilities, section states and allowed actions.
- GET /records/{entity_type}/{id}/focus: scoped actionable work, due/owner/source
  filters and cursor. Include permission-filtered counts.
- GET /records/{entity_type}/{id}/events: cursor, event-type filter and explicit
  record/customer scope. Return stable normalized event IDs.
- GET /records/{entity_type}/{id}/relations: relation type and pagination.
- Mutations call existing source-domain services with their permission, version,
  validation and audit rules. Aggregation is not a bypass around those services.
- Add relation rows only after checking existing CustomerLink/communication binding
  and commercial context facilities. Index tenant + relation target + source.
  Follow-up context additions need compatible SQLite/PostgreSQL migrations.
- Cache keys include user, organization, branch/workspace, entity, scope and filters.
  Invalidate after actions and identity changes; cancel stale requests on selection.

5. PMS TASKS AND FOLLOW-UPS: REQUIRED PRODUCT BEHAVIOR

One Tasks & Follow-ups queue in PMS with Today, Overdue, Upcoming, Assigned to me,
Assigned by me, Team, Completed and All; filters for customer, contact/lead, project,
assignee, priority, due range and source. Calendar/list first; reuse existing task
views rather than requiring a new task engine or another board implementation.

Include three source types with distinct labels:
1. PMS task: delivery/execution workflow, dependencies, progress/review remain PMS.
2. PMS task follow-up entry: tied to the original task; complete via entry action.
3. Shared customer/service follow-up: due commitment; complete/reschedule through
   existing service APIs. Add validated optional project/task context when needed.
CRM activities/tasks can be surfaced by an adapter where authorized; never clone
them into PMS merely to display them.

An item has one source of truth and one completion state. If an explicit workflow
creates a PMS task from a service commitment, store a unique source link, display
one combined focus item and define completion synchronization and retry behavior.
Do not automatically equate task completion, successful contact and service outcome.

Create from any 360 view pre-fills authorized context and assignment choices.
Require title, due datetime/timezone and assignee according to source workflow;
allow outcome/note plus next follow-up in one transaction where supported.
Show reminders, recurrence and escalation state accurately. Customer-only service
follow-ups remain supported; lead-only scheduling should use the lead workflow
until a validated subject model is introduced. Existing records must not be lost.

6. DELIVERY PHASES AND ACCEPTANCE GATES

Phase 0 — Baseline and contract (2–3 engineering days)
Owners: frontend + backend + QA.
Walk every active CRM/PMS/SRM entry route with representative roles; inventory
provider APIs and identity mappings; reconcile old reports; agree selected-record
versus customer scope and annotate screenshot layout for lead/contact/customer/task.
Gate: route matrix and canonical identity contract approved in project review;
no duplicate backend model introduced without a reuse assessment.

Phase 1 — Identity and aggregation (4–6 days; depends on Phase 0)
Owners: backend + QA.
Implement provider authorization, summary/focus/events contracts and paging;
reuse CustomerLink, add necessary relations, indexes and migrations; preserve
unmapped records with actionable reconciliation. Cover empty/restricted/failed states.
Gate: cross-tenant, branch, project and financial negative tests pass; same-name
customers and mismatched IDs cannot combine; lead without customer can open 360.

Phase 2 — Shared shell and CRM rollout (4–6 days; depends on Phase 1 contracts)
Owners: frontend + design + QA.
Build responsive shell and launcher; migrate company profile, leads, contacts,
Relationship Hub, account details and Deal 360. Replace customer360For content.
Integrate existing action dialogs and focus/history sources.
Gate: all CRM selection paths use consistent 360; no placeholder metrics; back,
refresh, direct links, context actions, conversion and mobile assignment work.

Phase 3 — PMS Tasks & Follow-ups (4–6 days; depends on Phases 1–2)
Owners: frontend + backend + QA.
Add queue/route/navigation, adapters, validated context relations, active task
workspace/customer chips and project/client entry points. Reuse reminder engine
where applicable; define completion mappings; preserve both task experiences.
Gate: create/complete/reschedule from PMS and customer 360 reflects the same source
record; no duplicate commitments; inherited and explicit relations are distinguishable.

Phase 4 — SRM and adjacent navigation (3–5 days)
Owners: frontend + backend + QA.
Move SRM search to the shared customer workspace; integrate commercial record
customer chips, orders, invoices, collections and POS view action. Add permission-
scoped commercial lists and context-preserving deep links. Check FAM/search links.
Gate: financially restricted users see no hidden figures/counts; transaction-free
customer still opens; POS cart and payment state survive profile open/close.

Phase 5 — Migration, UAT and rollout (3–5 days)
Owners: QA + frontend/backend.
Reconcile legacy identities without name-based joins; rollout behind per-module
feature flags; monitor provider latency/error rates; retain old URL compatibility.
Gate: no new task/follow-up workflow regressions, accessibility checks and role
matrix complete; documented rollback switches views without reverting business data.

Estimate: 20–31 engineering days of scoped effort, before live baseline findings;
not a committed calendar schedule. Frontend shell work may overlap backend work
after contracts stabilize. Staffing and reconciliation volume affect elapsed time.

7. VALIDATION MATRIX

- Identity: unconverted lead without company; individual customer; company with
  several contacts; same name across tenants/branches; merged contact; converted
  lead; unmapped PMS client; multiple projects; transaction-free customer.
- Permissions: admin, sales owner, sales viewer, PMS project member/nonmember,
  collections-only, invoice-only, no profitability permission, cross-branch user.
  Verify direct URLs, provider endpoints, counts, exports and attachment downloads.
- Actions: note, call outcome, meeting, task, follow-up, reschedule, completion,
  reassignment, file upload, draft vs send, delivery failure, opt-out, recurrence,
  reminder retry and duplicate submission. Stale versions yield a recoverable conflict.
- UI: every list/popup/full route, related-record back stack, keyboard focus/Escape,
  screen reader labels, narrow mobile viewport, draft preservation, slow requests,
  rapid record switching, section failures and stale-cache isolation.
- Timeline: stable paging at identical timestamps, correct timezone display,
  no source duplicates, accurate creator/action, completed work retained in history.
- Performance: agree a seeded representative dataset; proposed target p95 summary
  API <=800ms and initial usable workspace <=2s in staging conditions; lazy-load
  feeds, prevent N+1 joins, cap page sizes and record measured results. Targets are
  acceptance proposals, not current measurements.
- Existing tests to extend: backend/tests/test_srm_customer_360.py,
  test_service_follow_ups.py, test_pms_workspace_activity.py,
  test_customer_identity.py, test_customer_communications.py; browser suite
  playwright/srm-customer-360.spec.ts and customer-communications.spec.ts.
  Existing SRM UI test checks section rendering/errors; extend to real selected-
  record interactions and permission/content assertions. Test presence is not a pass.
