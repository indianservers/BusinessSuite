What the repository actually shows

This is a source-code review of the current working tree, including existing uncommitted changes, plus official competitor documentation. It is not a live usability test, production audit, or certification of payroll calculations. “Present” means code was found, not that the feature is complete or production-proven. The older May payroll plan is not used as the current gap inventory.

  • Existing foundations: employee directory filters, salary assignment/history, salary revision requests and batches, arrears, off-cycle runs, payroll payment batches, GL journals, payroll budgets, tax declarations, loans, full-and-final settlements, expense claims with manager/finance approval and payroll linkage, and asset assignments with return and acknowledgement fields.
  • Observed UX gap: PayrollPage contains numeric Employee ID and Dept ID inputs across operational tools. It also displays internal IDs in several result lists.
  • Observed asset gap: AssetsPage exposes create, assign, search, and inventory status. It loads only the first 100 employees for assignment; its selector includes every status other than Assigned, so repair/retired inventory can appear as choices. Server validation needs separate verification.
  • Existing employee context: EmployeeDetailPage already shows salary history and asset counts. The target is richer actions and connected ledgers, not recreating these features.

Comparison with Keka and Zoho

Compare BusinessSuite with Keka's HR suite and with Zoho Payroll + Zoho People + Zoho Expense where HR and expense scope is required. Do not attribute the combined Zoho suite to Payroll alone. Vendor features can depend on plan, region, or configuration; public documentation does not prove actual task completion speed.

  • Compensation planning: Keka documents review cycles, manager recommendations, budget controls, equity checks and payroll handoff. BusinessSuite already has revision batches and payroll budgets; the principal proposed gap is an integrated manager-facing increment cycle. Keka compensation planning.
  • Approval clarity: Zoho Payroll documents bulk revision approvals and conditional approval rules. BusinessSuite has revision and workflow foundations; verify configurable routing and expose approver, reason and next step directly in the increment flow. Zoho approval lifecycle · Zoho approval configuration.
  • Employee expenses: Keka documents receipt scanning and expense oversight across teams and cost centers. BusinessSuite stores receipts, two-stage approvals and payroll linkage. Add or validate receipt capture, policy checks, employee-level statements and payout reconciliation. Keka expense features — US page, regional availability unverified.
  • Assets: Keka's published customer case study shows an asset request workflow with requester, department, status and waiting-on context. BusinessSuite has inventory/custody foundations; the reviewed asset UI lacks equivalent request and custody workflow visibility. Keka asset workflow case study. Zoho Payroll asset-custody capability was not established in this review.
  • Connected HR/payroll/finance: Zoho documents People-to-payroll integration and Expense-to-payroll reimbursement integration. BusinessSuite already links claims to payroll; its opportunity is a single employee context with traceable handoffs and reconciliation. Zoho People payroll integration · Zoho Expense integration.
  • Payroll lifecycle: Keka describes validations, approval checkpoints and audit trails. BusinessSuite has corresponding models and tests; verify the full run journey before claiming parity. Keka payroll.

Suggested navigation and daily journeys

People: Directory → Employee 360 → My Team. Pay: Payroll cycles → Compensation & increments. Operations: Expenses → Assets → Approvals. Self-service: My Pay → My Claims → My Assets.

Manager: My Team → pending decisions → employee context → decision with reason. Payroll operator: select period → fix blockers → review changes → approve → pay → reconcile → publish. Employee: capture receipt → see policy check → submit → track approver → see payment reference.

The 100-item checklist

P0: first release · P1: next release · P2: later. Improve: extend a reviewed screen/foundation · Add/verify: proposed capability whose absence is not proven · Verify: validate existing behavior and expose it clearly. Checkmarks are local planning selections, not proof of implementation; use Export to save them.

Build order and completion gates

  1. Release 1 — connected daily work: Employee 360, searchable employee selectors, My Team decisions, asset custody/return, expense ledger, payroll readiness. Complete P0 items before broadening scope.
  2. Release 2 — compensation and control: manager increment planning, budgets, effective-date previews, policy-driven claims, payment reconciliation, exit clearance.
  3. Release 3 — optimization: scanning, integrations, cost analytics, saved reporting and automation.

Dependencies: stable employee identity and scoped permissions → employee-linked ledgers → approval routing → payroll inputs and effective dates → payment and accounting reconciliation. Asset recovery and expenses must feed settlement through reviewed, traceable adjustments.

Proposed usability gates, not measured results: find an employee within 10 seconds; review a routine claim within 60 seconds; assign an asset within 60 seconds; see a payroll blocker and open its fix within two actions. Validate with HR, a team manager, finance and an employee using realistic seeded data and mobile layouts.

Release acceptance scenarios: joiner with missing bank data; backdated increment; employee beyond the first 100 directory results; rejected/partly approved expense; failed payment retry without duplication; asset return during exit; manager attempting access outside their team; salary export by an unauthorized role. Payroll compliance and bank-format correctness require separate jurisdiction-specific validation.

Planning report only. No application behavior was changed. Checklist priorities are recommendations; no effort estimates or competitor parity percentages were invented.
