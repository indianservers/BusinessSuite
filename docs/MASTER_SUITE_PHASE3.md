# Master Suite Phase 3: enterprise control plane

Implemented in the existing BusinessSuite repository on 2026-10-26. This is an implementation and verification report, not a declaration that every three-phase acceptance criterion has been met. Production deployment remains blocked by the items below.

## Audit of Phases 1 and 2

Phase 1 already provides real users/access matrices, module roles, companies/branches/departments, entitlements, security/session administration, audit and user access 360. Those routes and their persisted data were retained. Phase 2 already provides shared policy/event/document records, immutable workflow versions, a managed service identity, durable automation jobs, approval snapshots, provider gateways and the visual builder. Existing gaps are recorded in `MASTER_SUITE_PHASE2.md`; they were not reclassified as complete simply because Phase 3 adds navigation.

The Phase 3 audit found global legacy configuration paths, absent company attribution in HTTP metrics, tenant-less subscription assignments, and a Business OS middleware path that could seed an organization which did not exist. Remediation restricts legacy global administration to Super Admin, adds explicit company subscriptions and HTTP audit context, and rejects unavailable organization contexts. The commercial isolation fixture now creates a real second company, retaining its original denial assertions. New analytics tests explicitly remove HR access rather than assuming an account with `employee_view` has no HR rights.

## Routes and implementation inventory

All new UI sections are under `/admin/control/enterprise/`. All new APIs are under `/api/v1/access/enterprise`. Existing `/admin/access`, `/admin/control/*` and `/admin/control/services/*` routes remain intact.

1. **Master control center — working enterprise extension.** `overview` shows scoped company/module counts, observed API activity, operational signals and linked actions. Reuses Phase 1 navigation, authorization, password step-up, mutation limits and append-only access audits. Module- and company-specific business metrics remain in authorized source views rather than a privileged global sum.
2. **Analytics — working scoped sources and saved layouts; broader business intelligence incomplete.** `analytics`, APIs `/analytics`, `/analytics/export`, `/policies?kind=dashboard` and `/relationships`. Current sources: CRM leads/pipeline, PMS projects/tasks, SRM invoices, HRMS employees. Aggregation occurs in SQL under the existing record-scope adapter, with company, supported branch/department and date filters. Unsupported organizational filters return an error. Currency totals are separated. The dashboard studio adds/reorders/resizes widgets, saves/clones layouts and shares presentation with native role IDs. Each viewer reauthorizes every widget. Time charts use actual creation dates; funnels describe status distributions rather than inferred conversion. CSV exports enforce export rights, apply filters and neutralize spreadsheet formulas. Relationship tracing uses persisted Business OS links and authorizes both records; it does not match names/amounts.
3. **Licensing — working configurable plans and company assignment.** `licensing`, APIs `/plans`, `/subscription`. Extends existing TenantSubscriptionPlan/TenantSubscription tables. Supports optimistic edits, module lists, seats, storage/AI/automation/API limits, support level, billing interval, explicit status, renewal/grace policy and a scheduled plan change. Existing Business OS entitlement checks narrow native route and service access. No billing collection is implemented; billing outages cannot suspend customers automatically. Existing data is preserved on changes.
4. **Health monitor — working observed signals, incomplete infrastructure adapters.** `health`, `/health`. Real database probe, pool counts where exposed, company-attributed request/error counts, bounded latency percentiles, existing workflow/email queue status, managed-document bytes. Missing frontend probes, worker heartbeat and CPU/memory exporters show unknown. A reachable database does not establish worker/frontend health. Historical logs without reliable tenant attribution are excluded from company metrics.
5. **Error center — working grouped HTTP failures.** `errors`, `/errors`, error-resolution policies. Groups sanitized existing audit records by module/registered endpoint/error type, with frequency/first/latest and explicit review state. Credentials, exception messages and payloads are not exported. It is not a general external log collector.
6. **Backup/recovery — existing service integrated and tested offline.** `backups`, `/backups`, `/backups/policy`, `/backups/{id}/verify`, recovery-request policies. Uses the existing archive scheduler/catalog/checksum/extraction and PostgreSQL tools, not a replacement backup format. Backup policy edits use existing frequency/retention controls. Requests require privileged authorization, non-production procedure and independent approval. Manual status cannot manufacture verification. HTTP verification restores SQLite into a temporary directory; PostgreSQL full restoration was tested separately in a guarded disposable database. No HTTP endpoint restores a live database. Infrastructure encryption and off-site durability still require deployment verification.
7. **Feature flags — working company/module targeting and rollback.** `flags`, `/flags`, `/flags/evaluate`, `/flags/{id}/rollback`. Reuses BOSFeatureFlag and its existing JSON metadata. Targets native roles/users/branches, environment, stable percentage assignment and expiry. Missing flags default off. Snapshot rollback increments versions and is audited. Evaluation first enforces company membership, entitlement and module access. Flags cannot grant permissions. Module authors must explicitly consume optional feature decisions in their product code; registering a flag does not rewrite every existing screen.
8. **Branding — working authenticated company theme; full white-label coverage incomplete.** `branding`, branding policies and `/branding`. Validated app name, hex colors, radius and text contrast. Sidebar identity and authenticated application design tokens consume the current company theme and reset on context change. Logo/footer/domain metadata has a configuration path, but unauthenticated login branding, invoice/report/email rendering adapters and domain/TLS provisioning are not certified complete. No DNS or TLS configuration was changed.
9. **Governance — working classification/hold configuration and conservative enforcement; no generic purge.** `governance`, governance policies. Registered entity types have classifications, role restrictions, retention references and holds. Shared record reads and analytics apply classification. Native business routes use a conservative module-wide restriction when fine entity-specific policy adapters are unavailable. Active holds block destructive module operations; existing HR retention additionally checks configured statutory blockers and governance holds. Financial/employment data is not deleted by a new generic cleanup engine. Retention references are administrator-supplied policy evidence, not legal certification. Dependency-aware archival/purge workflows remain incomplete.
10. **Support — working existing helpdesk ticket/incident lifecycle.** `support`, `/tickets`, `/tickets/{id}`, `/tickets/{id}/comments`. Extends HelpdeskTicket for company/module context, optional employee linkage and optimistic versions. Supports actual ticket creation, incident classification, assignment, priorities, status and persisted comments. Assignees must belong to the company. The shared document service has a `support_ticket` read adapter, although a dedicated attachment picker is not implemented here. Support-access requests are time-bounded review records and grant no impersonation or hidden access. Automated provisioning/revocation of temporary support grants is still unavailable.
11. **Action center — working operational aggregation.** `actions`, `/actions`, `/alerts/evaluate`. Includes actual failed/uncertain workflow jobs, unresolved HTTP error groups and open support tickets, with links to their real administration pages. Existing approval/security inboxes remain authoritative. Operational alerts persist in existing notifications/delivery logs with company serialization and a 15-minute cooldown. Evaluation is explicit; a continuously running alert scheduler and complete escalation policies are not implemented.
12. **Module integration coverage — live discovery plus regression evidence.** `coverage`, `/catalog`. Every catalog-discovered module appears, including shared groups. The view distinguishes available record adapters/analytics from unregistered domain adapters. A central interface is not a claim that every route has been security-certified. Existing tests exercise CRM-to-SRM conversion, connected commercial invoicing/payments, intern management, native automation and AI tool authorization. Full browser sales/PMS/intern/AI lifecycles remain unverified in this change.
13. **Performance — measured limited profile.** Active seat counts now use SQL aggregation rather than loading complete user profiles. Analytics aggregates/paginates on the server; error/ticket views are bounded; routes are lazy loaded; stale asynchronous page responses are ignored. The opt-in load profile uses 10,000 accounts, 100 companies, 25 registered module definitions, 10,000 CRM leads and 20 sequential analytics requests. It is not a concurrent production capacity certificate. Resource telemetry and concurrent CRM/workflow load remain unverified.
14. **Security fixes — validated boundaries, not an exhaustive penetration-test certificate.** Tests cover tenant/owner aggregation, native entitlement denial, restricted-policy native bypass, export rights, protected configuration, stable targeting, optimistic writes, quota limits, immutable approvals and inherited SSRF/replay/document checks. Backup verification uses non-production destinations. The security checklist is informed by [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) and [ASVS](https://asvs.owasp.org/). Remaining inherited boundaries are deployment blockers below.
15. **Automated tests — executed, results recorded below.** New files: `test_enterprise_control.py`, `test_enterprise_browser.py`, `test_enterprise_load.py`; existing access, shared-service, security and commercial tests are retained. Browser traffic is forwarded unchanged to the actual FastAPI test application and disposable database; responses are not fabricated.
16. **Deployment documentation — included below.** No target application database migration, deployment, live domain update, billing mutation or external provider setup was performed.
17. **Architecture documentation — central, reusable design.** Enterprise API/services reuse AccessPolicy/AccessMembership/AccessAudit, ServicePolicy, the existing subscription tables, BOSFeatureFlag/BOSEntityLink, HelpdeskTicket/Reply, AuditLog, Notification and existing backup infrastructure. No second authentication, workflow, notification or backup engine was created.

## Quota and safety semantics

Company subscription limits apply only when explicitly assigned with enforcement enabled. Module entitlements are backend restrictions; administration remains available for repair. Scheduled changes resolve when effective, without deleting customer data. Seat checks guard native global user creation into its existing primary company and new explicit memberships; not every historical HR/import provisioning path has been migrated. Storage quotas cover shared document versions. AI and automation quotas cover the shared gateway/jobs per UTC calendar month; Phase 2 per-module daily AI limits still apply. Authenticated native business API attempts reserve a monthly allowance durably before endpoint mutation; failed attempts count. Platform administration is excluded so administrators can repair licensing. Other legacy providers/provisioning/import paths need coverage before claiming universal commercial metering.

If an automation cannot reserve its quota, its outbox event is recorded as `quota_blocked`; it is not reported as successfully dispatched. There is no silent data purge, unrestricted impersonation or blind retry of an uncertain external write.

## Database changes and rollout

PostgreSQL revision `pg_20261026_026_enterprise`, after `pg_20261026_025_shared`; SQLite-tree revision `20261026_026_enterprise`, after `20261026_025_shared`.

Changes: plan config/version; company-specific subscription config/version and unique company assignment; company attribution and operational index on HTTP audit logs; company/module/details/version on existing helpdesk tickets, with employee linkage optional. Only the latest legacy singleton subscription is attributed to company 1; other legacy rows remain historical. Helpdesk ownership backfills from employee branch. Historical HTTP records are not assigned to a tenant by guesswork. Review ambiguous legacy records before rollout.

Use the repository's existing deployment migration entry point with the correct environment. The canonical `backend/alembic.ini` selects the deployed migration tree through the existing environment configuration. Back up and inventory the target first, review all pending Phase 1/2/3 revisions together, apply them on a staging copy, then run authorization/tenant/provider smoke tests. Do not point the disposable test runner at an application database: it intentionally recreates only guarded `business_suite_*_test` databases.

Rollback: disable workers and optional features first, retain/export new configuration and support records, and restore a verified backup or use a reviewed downgrade. Downgrade refuses employee-less central tickets that the older helpdesk schema cannot represent. Do not discard audit or business records merely to make a downgrade succeed.

## Recovery runbook

Use existing `scripts/data_recovery.py` for backup/checksum verification and extraction into a new offline directory. For PostgreSQL, use existing `scripts/postgres_restore.py` with an explicitly configured EMPTY non-production database; verify destination configuration before running it. The automated recovery test additionally guards test database names, restores through `pg_restore --exit-on-error --single-transaction`, checks probe rows/schema and file bytes, and drops only its explicitly named disposable restore target.

Keep database and object-storage recovery points consistent; separately secure encryption keys/provider credentials and deployment configuration. Verify migrations, authentication, memberships, entitlements, documents, invoice snapshots and workers after recovery. RPO/RTO must be agreed deployment objectives and measured under the real infrastructure; local test duration is not a production recovery-time guarantee. Off-site copies, encryption at rest, retention durability and operational alert routing require infrastructure evidence.

## Unresolved production blockers and remaining scope

- The inherited Phase 2 audit still identifies incomplete legacy public intake/communication tenant boundaries, service identity migration, reconciliation/delegation administration and the full set of business recipes. Those routes need a complete threat-model and tenant regression pass before a platform-wide security sign-off.
- The separate `inventory/vyapara_erp` Flask subtree is not certified as a centrally authenticated/tenant-isolated deployment by the main FastAPI module catalog. Independently deployed subapplications need explicit identity and entitlement adapters.
- Live email/AI/integration credentials were not supplied or exercised. No live AI model, end-recipient email delivery, external webhook delivery or billing provider is certified by these tests.
- This change does not execute all requested company onboarding, complete sales, PMS, intern and AI browser lifecycles. Existing integration tests are useful evidence, not a substitute for those missing browser paths.
- Analytics lacks the full finance/cash-flow/profitability, intern/batch and conversion dashboards, complete organization filters across every source, and comprehensive widget-sharing administration. Unsupported relationships are omitted rather than inferred.
- Full support-access grant provisioning/revocation, attachment UX, complete incident/error drilldown, universal legal retention/archival/purge adapters, unauthenticated white-label rendering, and automated operational escalation remain incomplete.
- Frontend availability probes, worker heartbeats, CPU/memory telemetry, production encryption/off-site backup verification, concurrent workload targets, P99 under sustained load and measured production recovery objectives remain unverified.

**Acceptance status:** the implemented enterprise controls are testable and connected to real services. The complete three-phase platform is not yet approved for production deployment. These blockers must be resolved or explicitly accepted through the organization's release process; no deployment is recommended while critical tenant-boundary work remains unresolved.
