BEFORE ANY PRODUCTION RELEASE
0. Configure DATABASE_URL and MIGRATION_DATABASE_URL with the installed driver:
   postgresql+psycopg:// (Psycopg 3). Use the direct Neon host for migrations,
   retain sslmode=require or stronger, and never print credentials. A raw
   postgresql:// MIGRATION_DATABASE_URL selects the absent psycopg2 driver.
1. Record the candidate manifest fingerprint, source/build hashes, test reports,
   current production deployment, database revision and configuration versions.
   The local candidate has a SHA-256 identity distinct from its base Git commit.
   Do not deploy a later mutable working-tree checkout in place of that candidate.
2. Confirm the rollback deployment still exists and the current alias mapping:
   vercel inspect https://app.dsbchartered.com --scope team_bE8rRsbbyPR30IkE3xI4oHso
3. Capture a production backup through the approved secure database connection.
   Set DATABASE_URL in the process using the secret manager, verify its host and
   database without printing credentials, then run from the repository root:
   backend\venv\Scripts\python.exe backend\scripts\postgres_backup.py --output .local\release-backups\pre-release-20261112.dump
   Protect this production-data backup. Do not commit, upload to chat, or include
   it in the candidate archive. Record checksum and the time writes were paused.
4. Restore the backup into a NEW EMPTY isolated database, using a separate
   DATABASE_URL for that target and its required PostgreSQL client tools:
   backend\venv\Scripts\python.exe backend\scripts\postgres_restore.py .local\release-backups\pre-release-20261112.dump
   The restore script does not create a database or choose a safe target for you.
   Confirm the destination is empty and is not the production database first.
5. Verify migration revision, representative record counts, authentication and
   financial reconciliation on the restored copy. Confirm the previous app can
   run with the schema that will remain after release. Never assume alias rollback
   reverses a migration. No new migration files were found between the observed

tenant/branch leakage, missing/duplicate invoices or projects, incorrect payment
allocation, lost HR updates, or a critical workflow regression. Preserve request
IDs, logs, candidate fingerprint and affected record IDs before changing traffic.

Keep writes paused. Preserve a new backup of the incident state and inventory
post-backup writes. Restore the pre-release backup to a NEW EMPTY database using
the procedure above, verify its integrity, and reconcile later valid business
transactions before switching the application connection. An old backup can lose
newer invoices, payments and HR changes; do not overwrite the current database or
run alembic downgrade headlessly as a generic rollback step. Routing, configuration,
database and private object storage recovery are separate actions.
